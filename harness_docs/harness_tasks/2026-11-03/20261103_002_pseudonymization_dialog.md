### В6 (03.11, инициатива пользователя): Постоянная разметка сущностей с ULID-идентичностью — предложение P1

**Суть предложения пользователя (концепция).** При открытии markdown-документа,
прежде чем работать, настоятельно просить (или принудительно требовать)
выполнить NER-разметку. В редакторе уже есть специальный вид меток (ULID-чипы)
— тем же способом можно разметить и markdown-файл. При отправке в модель —
прям словарь замен. ULID использовать для однозначной идентификации и быстрого
обратного ремаппинга. Цель: одно и то же значение в разных markdown-документах
мапилось на один и тот же маскированный псевдоним и корректно возвращалось;
тогда запрос, объединённый по нескольким документам, свяжет сущности между
собой и модель даст правильный ответ.

**Оценка агента: поддержать.** Что даёт против «NER при каждой отправке»:

| Свойство | Разовый NER при отправке | Постоянная разметка + реестр (P1) |
|---|---|---|
| Стабильность псевдонима | в пределах прогона | одинаковая всегда — ULID-идентичность |
| Ложные срабатывания | при каждой отправке | один раз, при ревью разметки |
| Связность между документами | нет | да — один плейсхолдер во всех документах запроса |
| Стоимость отправки | NER-прогон | подстановка словарём, O(вхождений) |

Прецеденты в коде: ULID-чипы (`harnessUlidExtension.ts`,
`HarnessUlidPopover.tsx`), схема ссылок (`harnessUlidLink.ts`), JSONL-реестр
(`parseDocumentsJsonl`), opaque-id (`src/lib/agent/ids.ts` — сессионные;
P1 добавляет четвёртый, постоянный слой идентичности). Небольшой новый код:
генератор ULID (в приложении пока только парсинг, генерации нет).

**Уточнение агента к «словарь замен в промпт»:** отправлять словарь можно
только в одну сторону — `плейсхолдер → тип`; соответствие
`плейсхолдер → значение` в промпт не попадает никогда. Словарь «алиас → тип»
помогает модели писать связный текст и связывать сущности.

**Что amend'ит P1 (статус — до решения):**
- D4: формат плейсхолдера → `[[VAS_<TYPE>_<ULID>]]` вместо счётчика прогона;
- D8: маппинг перестаёт быть «только в памяти» — появляется постоянный
  реестр (ULID → тип → вхождения). Периметр доверия не расширяется: значения
  и так лежат в тех же документах на том же диске; в audit и логи значения
  по-прежнему не попадают;
- T3: из «подсветки сущностей» вырастает в «реестр сущностей + разметка +
  чипы» (detect → ревью → сохранить → метки в редакторе);
- UX-барьер: мягкий по умолчанию (баннер «есть неразмеченные сущности»,
  отправка возможна, в audit — отметка), жёсткий — настройкой
  `masking.require_markup`.

**Открытые развилки P1:** (1) хранение разметки — sidecar-реестр
(`entities.jsonl` рядом с workspace) vs инлайн-разметка в тексте markdown vs
гибрид со скрытым конвертом (как harness-yaml); (2) значения в реестре —
открытым текстом или Fernet-шифрование (крипто уже есть); (3) пере-якорение
вхождений при правках документа (по образцу rebase proposals: точный текст +
хеш контекста, stale при расхождении); (4) где живёт реестр при
multi-workspace.

### В7 (03.11): Закрытие развилки (1) — хранение разметки

**Ответ пользователя:** не против хранения рядом с документом в JSONL
(harness-репозиторий), но ожидает, что разметка будет «интегрирована в
Markdown»: при разметке фиксируется, что строковое значение принадлежит NER,
рядом проставляется чип — видимый и в просмотре, — который показывает, куда
идти и во что значение смапается при send.

**Закрытие: sidecar-реестр + чипы как слой отрисовки.** Уточнение агента:
чипы ULID устроены иначе — там разметка живёт в самом файле
(`[имя](harness-ulid:…)`), чип — её отрисовка. Для сущностей наоборот: файл
остаётся чистым markdown, чип строится из реестра как декорация. Слои:

1. **файл .md** — не меняется никогда (round-trip, GitHub, чужие инструменты);
2. **реестр** `entities.jsonl`: `{ulid, type, value, occurrences:[{doc, start,
   end, ctxHash}]}`; harness-папка → `harness_docs/harness_index/entities.jsonl`
   (рядом с documents.jsonl), обычная папка → рядом с workspace; путь
   определяется существующими `isHarnessRepoDir`/`findHarnessIndex`;
3. **редактор** — WYSIWYG и Markup: чип-декорация над размеченной строкой,
   поповер: тип, алиас, вхождения, переход, «снять разметку»;
4. **просмотр** — превью (diplodoc → HTML): те же чипы, read-only; прецедент —
   `previewLinks.ts` (вшивание ссылок в HTML по совпадению текста);
5. **send** — подстановка из реестра, в промпт словарь «алиас → тип»,
   ремаппинг ответа по ULID.

Следствие (осознанно): offsets в реестре плывут при правках — пере-якорение по
образцу rebase proposals (точное значение + хеш окружения; не сошлось →
вхождение stale, чип гаснет, «требует переподтверждения» в панели реестра).

Остаток развилок P1: (2) значения в реестре — открытым текстом или Fernet;
(4) реестр при multi-workspace. Развилка (3) закрыта решением выше.

**Дополнение пользователя (следующим сообщением):** переживает, что при

**Закрытие агента — хранение переворачивается:** источник истины — **сам
документ** (инлайн-разметка), `entities.jsonl` становится **производным

«рассыпаться» навсегда — худший случай, пересканировать. Разметка едет вместе
с документом при передаче. Бонус: если носитель привязан к значению физически,
пере-якорение (следствие из В7) почти не нужно.

Два носителя:

| | (а) скрытый комментарий-конверт | (б) чип-ссылка |
|---|---|---|
| Вид в файле | `<!-- [<[entity]] id:01J… type:person [[entity]>] -->` перед значением | `[Иван Иванович Иванов](vas-entity:01J…)` |
| Прецедент | конверты harness-yaml/task-yaml — только в шапке; инлайн-комментарии посреди текста в WYSIWYG не проверялись — нужен спайк round-trip | **доказан**: ULID-ссылки round-trip (20261027_002), санитайзер приучен, чип+поповер+переход готовы |

| Чужие инструменты | комментарий не рендерится — разметку видит только Vasyavig | видна обычная ссылка: текст читается, href «мёртвый»; знающий схему видит NER-разметку |

### В9 (03.11): Закрытие развилки носителя — чип-ссылка

**Уточнение пользователя (исправление трактовки агента):** «мой ответ —
чип-ссылка вполне подходит, и она видна». Носитель — **чип-ссылка**
`[значение](vas-entity:<ULID>)`; скрытый комментарий-конверт отклонён.
Зафиксированное требование: **правки документа (поправили имя) должны влечь
повторную разметку — прогон**.

**Цикл re-markup при носителе-ссылке:**

1. Значение = текст ссылки: правка имени правит значение, разметка (ULID в
   href) не теряется и не отлипает — физически привязана.
2. Скан (сохранение/открытие/запуск прогона): сравнение текстов ссылок с
   кэшем индекса `entities.jsonl` (значения открытым текстом — В8).
3. Текст изменился → сущность **changed**: «значение изменилось — та же
   сущность или новая?» (правка опечатки → та же; смена фамилии → новая;
   решает пользователь).
4. **Прогон re-markup** (требование пользователя): (а) неразмеченные значения
   → предложить разметить; (б) changed → пере-подтвердить; (в) исчезнувшие
   ссылки → вывести сущность из реестра.
5. Производный индекс пересобирается тем же сканом (read-only кэш, как
   documents.jsonl после `make doc-index`).

Плюсы носителя-ссылки против конверта (почему риск ниже): round-trip доказан
на ULID-ссылках (20261027_002), санитайзер приучается по готовому рецепту
(allowedSchemes), чип+поповер+переход готовы (`HarnessUlidPopover`), чипы
видны и в чужом рендере (текст читается), хеш сверения не нужен.

D4 amendируется окончательно: алиас `[[VAS_<TYPE>_<ULID>]]`, ULID из href; в
промпт — словарь «алиас → тип», никогда «алиас → значение».

## 4. Принятые решения

- **D1.** ML-детектор в roadmap не входит. Возврат к вопросу — отдельной
  задачей при условиях §7.
- **D2.** Основа NER — правила: `ru-compromise` (114 КБ gzip) + `lvovich`
  (6.5 КБ) + ~100 строк своих regex ≈ **120 КБ gzip** к бандлу ~9 МБ, без wasm,
  без Python, оффлайн по умолчанию.
- **D3.** NER — сменный детектор в общем реестре детекторов, а не отдельный
  механизм: добавление NER не меняет каркас маскирования.
- **D4.** Формат плейсхолдеров — `[[VAS_<TYPE>_<N>]]` (префикс `VAS_` снижает
  риск коллизии с текстом документа; §3.9 спецификации и §7 сводки расходятся
  — закреплён префиксованный). Одна сущность — один плейсхолдер в пределах
  прогона; разделитель проверяется на коллизию с текстом документа.
- **D5.** T1 — ядро без UI; превью (чипы, подтверждение) — T1b. До T1b
  маскирование выключено по умолчанию.
- **D6.** До T1b режим `preview` маскирует, но не запрашивает подтверждения:
  в панели — явное предупреждение, в audit — отметка, что подтверждения не
  было. Гарантия «секреты не уходят в модель» соблюдается.
- **D7.** `emailHtml` — без маскирования (§3.9: для писем с реальными именами
  псевдонимизацию отключаем). Механизм доступен, режим для письма — `off`.
- **D8.** Таблица маппинга — только в памяти: не в лог, не в audit, не на диск;
  в audit идут только счётчики и типы.

**Итоговые решения после P1 (В6–В9) — дополняют/заменяют D4, D8:**

- **D4'.** Алиас — `[[VAS_<TYPE>_<ULID>]]`: ULID сущности вместо счётчика
  прогона; одинаков во всех документах и прогонах.
- **D8'.** Источник истины — документ: разметка живёт в файле чип-ссылками
  `[значение](vas-entity:<ULID>)`; `entities.jsonl` — производный кэш
  (plaintext, значения открытым текстом — В8), пересобирается сканом;
  в audit и логи значения не попадают (как и было).
- **D9.** Модель получает маскированный текст + словарь «алиас → тип»;
  ремаппинг ответа — по ULID из реестра.
- **D10.** Re-markup (требование пользователя): правки документа → прогон
  по документам → changed (та же сущность или новая — решает пользователь),
  неразмеченные (предложить), исчезнувшие (вывести из реестра).

**Спайк `ru-compromise`** (временная директория вне репозитория, после прогона
удалена): `#Person → [Иван, Иванович, Иванов, Петров]`, `#FirstName`,
`#LastName`; `json({offset:true})` даёт точные символьные позиции
(`text.slice(start, start+len)` совпадает с найденным фрагментом) — этого
достаточно и для подсветки, и для маскирования; 0.24 мс/документ; билд
`builds/ru-compromise.mjs` самодостаточный (без import/require, browser-safe),
390 КБ raw.

Ограничения (подтверждены): `#Organization` — 0 %, `#City` в родительном падеже
(«в г. Москве») — 0 %, «Санкт-Петербург,» приходит с запятой.

**Свои правила для русского** (проверены исполнением):

| Признак | Полнота | Ложные срабатывания |
|---|---|---|
| Отчество (`-ович/-евич/-ич`, `-овна/-евна`) | ~95 % персон | **<1 %** |
| Инициалы + фамилия (`Петров А.С.`, `И. И. Иванов`) | ~90 % | ~2 % |
| Юр. формы (ООО/АО/ПАО/НАО/ФНС/ГК) | ~85 % орг | ~2 % |
| Гео-подсказка + предлог (`в г. Москве`, `на ул. Пушкина`) | ~70 % локаций | ~10 % (нужна пост-фильтрация «улица ≠ город») |
| Гео-словарь (из ru-compromise) | ~90 % городов | ~1 % |
| Бренды без юр. формы (Газпром, Сбербанк) | **0 %** | — нужен доменный словарь |

**Ловушка JS:** `\b` и `\w` не работают по кириллице
(`/(\bИван)/.test("Иван Иванов") === false`) — русские regex только через
lookaround `(?<![А-Яа-яЁё])…(?![А-Яа-яЁё])`.

**Рычаг расширения:** `ru-compromise` умеет `nlp.addWords({'Ромашка':'Organization'})`
— доменный словарь подгружается в рантайме, без пересборки бандла.

## 9. Условия возврата к ML-детектору (отложено)

1. Правил не хватает: нужна связывание сущностей (PERSON в свободном тексте
   правилами не вытянуть).
2. Домен документов совпадает с доменом обучения модели.
3. Готовность поставить модель **отдельным необязательным пакетом**, чтобы
   базовый клиент остался ~10 МБ; Apache-2.0-вариант (не CC-BY-NC).
4. Есть замеры на целевой машине: время на 100/500 КБ, память, время первой
   загрузки.
5. Машина состояний готова: `disabled | unavailable | loading | ready | error`,
   деградация к правилам, таймауты, отмена, кнопка «Проверить окружение».
