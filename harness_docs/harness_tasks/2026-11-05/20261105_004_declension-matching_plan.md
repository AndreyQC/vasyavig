## 1. Проблема

Матчинг неразмеченных значений (резолвер ULID в маскировании, unknown-known в
панели re-markup) работает **только по точному совпадению** с известными
формами. Склонённая форма, которую ещё никто не размечал («Ивановым И. И.» в
новом документе, когда в индексе только «Иванову И. И.»), не связывается:
per-run ULID → разрыв связности между документами — главный риск P1.

## 2. Решение

- **T3d-1. Генерация форм** (`src/lib/agent/masking/declension.ts`,
  `expandEntityForms(canonical, type)`): lvovich склоняет **от canonical**
  (именительного падежа) все падежи; результат — множество строк-форм:
  - `PERSON`: разбор canonical на части — фамилия, имя, отчество
    (`getMiddlenameGender` валидирует), инициалы (`А.`/`А.С.`); шаблоны
    «Фамилия И. И.», «И. И. Фамилия», «Фамилия Имя Отчество»; для каждого из
    6 падежей — `inclineLastname/inclineFirstname/inclineMiddlename`;
    инициалы не склоняются. Женские фамилии (Иванова → Ивановой) и
    несклоняемые (Шевченко) lvovich обрабатывает сам.
  - `LOC`: `cityTo/cityFrom/cityIn` (вин., род., предл.) + именительный.
  - `ORG/SECRET/EMAIL/PHONE/URL_CRED`: не склоняются — только canonical.
  - Кэш по `(ulid, canonical, type)` в Map (формы индекса читаются часто:
    резолвер на каждое значение детектора, скан репо).
- **T3d-2. Матчинг.** `matchEntityEntry` получает расширенный режим:
  сначала точное (forms ∪ canonical — как сейчас), затем сгенерированные
  формы (только для person/loc; регистр точный). Возврат — та же запись
  индекса; ничего в jsonl не пишется (generated — слой матчинга, не
  хранение; наблюдаемые формы дописываются как раньше — при разметке/сохранении).
- **T3d-3. Интеграции** (без изменений кода потребителей):
  - резолвер в `prepareModelStage` (`matchEntityEntry`) — неразмеченное
    «Ивановым И. И.» получает постоянный ULID «Иванову И. И.»;
  - `diffEntitiesScan.unknownKnown` — поиск по расширенным формам
    (перебор `forms ∪ canonical` заменяется на `expandEntityForms`);
  - `NerButton`-предложения — тот же `matchEntityEntry` (fuzzy включён).
- **T3d-4. Направление матчинга** — значение из текста против форм записи.
  Формы генерируются из canonical; если canonical сам в косвенном падеже
  («Иванову И. И.» как первый размет) — генерация от него неточна: сначала
  пробуем точные forms, потом генерацию; при канон-в-косвенном lvovich
  вернёт форму от косвенной — допустимое ограничение (canonical выравнивается
  при первом же переутверждении эталона).
- **T3d-5.** i18n не нужен (чистая логика); фикстуры — правдоподобные
  персоналии без секретных паттернов (§16).

## 4. Проверки

1. **Генерация**: «Иванов Иван Иваныч» → 6 падежей × 3 шаблона (Иванову И. И.,
   Ивановым, Иванова, И. И. Ивановым…); «Иванова Анна» → Ивановой;
   «Шевченко» — несклоняемое; город «Москва» → Москвы/Москву/Москве.
2. **Матчинг**: текст «Ивановым И. И.» при canonical «Иванову И. И.» → запись
   найдена (fuzzy); точное совпадение приоритетно; org — только точное.
3. **Интеграция**: maskText с resolver — неразмеченное склонённое значение →
   постоянный ULID (расширить vasEntity/agentStore-кейс).
4. `pnpm test`, `npx tsc --noEmit`, `npx vite build`.

## 5. Риски / ограничения

- lvovich — словарь окончаний: редкие фамилии/имена могут не склоняться
  (вернёт вход как есть) — безопасно (форма совпадёт с canonical).
- Ложные срабатывания fuzzy: короткие формы городов («Москве» уникальна, но
  «пушкина»-фамилии vs ул. Пушкина) — матч только по точному регистру и
  целому значению; NER-предложения по-прежнему предлагающие.
- Производительность: генерация ~18 строк на персону, кэш — не проблема.
- Не пишем generated-формы в `entities.jsonl` — файл остаётся словарём
  наблюдаемых форм (решение пользователя по виду строки).
