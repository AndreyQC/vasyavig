## Решение (пользователь)

**Справочник-first.** `entities.jsonl` — единственный источник истины по
сущностям; документы остаются чистыми; сущности в тексте показываются
runtime-подсветкой из справочника; чип-разметка — **точечный якорь** там, где
идентичность по форме текста неоднозначна.

## Почему (сжатая аргументация)

Чип в документе решает три задачи, которые форма текста не решает:

| Задача | С чипом | Без чипа |
|---|---|---|
| Различение однофамильцев | ULID в конкретном вхождении | все «Ивановы» — одна сущность |
| Якорь маскирования | `[[VAS_PERSON_01J…]]` → однозначное значение | алиас→значение глобальное |
| Детект дрейфа (re-markup) | «поправили значение, ULID тот же» | «Иванов И. И.» и «Иванов Иван Иваныч» неразличимы |

Поэтому чипы не убираем, а **понижаем в статусе**: точечный якорь вместо
массовой разметки. Массовую разметку заменяет справочник + подсветка.

## Что уже готово (не переделываем)

- `entities.jsonl` = `{ulid, type, canonical, forms[]}`; `forms` уже хранит
  несколько наблюдаемых текстов одной сущности → кросс-языковая и
  кросс-падежная связка («John Smith» ≡ «Иванов Иван Иваныч») выражается
  сегодня одной записью.
- Runtime-сопоставление со справочником уже работает в панели NER
  (`matchEntityEntry` + fuzzy по `expandEntityForms`) — не хватает только
  подсветки в самом тексте.
- ProseMirror-декорации уже строятся (`vasEntityExtension.ts`) — runtime-подсветка
  это другой источник данных, а не новый механизм.
- **NER (ru-compromise + lvovich)** — в guardrails его нет вообще (там только
  regex), он остаётся нашим источником PERSON/ORG/LOC.

**Оговорки по переносу в TypeScript:**
- Go RE2 не поддерживает lookbehind, JS — наоборот; в корпусе **lookaround не
  используется ни разу** (0 совпадений), поэтому конвертация сводится к флагам:
  инлайн `(?i)` (23 правила) → флаг `i` в описании правила; `(?-i:…)` — в
  отдельное правило.
- Нет `regexp/syntax` → автодоказательство «префильтр по ключевым словам не
  ломает recall» не переносится: префилтр включается **явным флагом правила**
  `prefilter_safe: true` + `keywords`, по умолчанию выключен.
- Нет аналога `regexpMaxLen` → верхняя граница длины алиаса задаётся константой
  в описании правила.
- Синтаксис и комментарии правил переносим **вместе** — комментарии содержат
  *почему* правило устроено так и какие FP были откачены.

## Цели

1. Справочник правится в одном месте, без правок документов.
2. В тексте документа сущности видны (бейдж типа) без разметки.
3. NER-подсказки пополняют **справочник**, а не документ.
4. Однофамильцы и одноимённые объекты различаются **связями между сущностями**.
5. Чип остаётся доступным как точечный якорь — и появляется **сам**, когда
   разрешение конфликта требует устойчивой привязки.

## Связи между сущностями и разрешение однофамильцев (ядро T6)

### Модель

- Справочник — **граф**: узлы (сущности) + рёбра (связи).
- Связи — отдельным файлом `harness_docs/harness_index/relations.jsonl`
  (рядом с `entities.jsonl`), запись:
  `{from: ulid, to: ulid, kind, confidence: "explicit"|"inferred", source?: docPath, evidence?}`.
- Виды связей:

| kind | Смысл | Пример |
|---|---|---|
| `works_at` | персона → организация | «Иванов Иван Иванович» → «ООО Ромашка» |
| `member_of` | персона/объект → проект | участник → проект |
| `role_in` | персона → роль в проекте | «заказчик» |
| `alias_of` | тождество двух записей | синонимы, кросс-языковые формы |
| `co_occurs` | **выведенная**: два значения встречаются в одном контексте | профиль соседства |

- Явные связи (`explicit`) ставит пользователь; `co_occurs` считается сканом
  (профиль соседства: для каждой сущности — top-N соседей с весом и списком
  документов; производный кэш, пересобирается сканом).

### Разрешение вхождения (порядок)

1. **Якорь** (чип) в документе → точный ULID, дальше не идём.
2. Единственное совпадение **формы** в справочнике → разрешено.
3. Несколько кандидатов (однофамильцы) → **контекст**:
   - контекст = Markdown-блок (абзац / строка таблицы), fallback — документ;
   - в контексте найдены другие известные сущности (организация, проект);
   - если у кандидата есть **явная связь** с такой сущностью (`works_at`,
     `member_of`) — кандидат выигрывает;
   - иначе — максимум по **профилю совместных появлений** в этом документе;
   - ничья → **конфликт**: панель выбора пользователем.
4. Разрешено → бейдж типа (при желании с уточнением: «ООО Ромашка»).

### Материализация якорей (чип появляется сам)

- После разрешения конфликта пользователем: записать **связь** (`works_at` и т.п.)
  **и** поставить **якорь** в конкретное вхождение документа — чтобы разрешение
  стало устойчивым к правкам текста.
- Автоматический режим (опция в настройках): якоря материализуются сами там,
  где форма неоднозначна в справочнике, но разрешение однозначно по связям.
  Итог: чипы появляются **только там, где они нужны**, а не по всему репо.

## Границы (что НЕ входит)

- Свободный чат, эскалация, write-path `documents.jsonl`.
- Визуализация связей сущностей (граф сущностей) — в бэклог.
- Импорт/экспорт справочника (YAML/JSON) — в бэклог.
- Менять маскирование и рецепты 8.3/8.4 — только точечно, если понадобится
  якорь для алиасов.

## Шаги

### T6-1. Модель справочника

- Запись: `{ulid, type, canonical, forms[], aliases[]}`.
  - `forms` — наблюдаемые в документах тексты (из разметки/скана);
  - `aliases` — ручные формы (в т.ч. кросс-языковые), **не теряются** при
    merge/скане (сейчас `mergeEntitiesIndex` сливает только `forms`).
- `canonical` — явное поле (сейчас = первая форма; при переходе — взять из
  существующей записи, не мигрировать автоматически).
- Бэкомпат: старые записи без `aliases` читаются как `aliases: []`; запись
  обновляется только при явном действии пользователя.

### T6-2. Панель «Справочник»

- Отдельная панель (не панель ассистента: справочник — per-harness-root, а
  ассистент — per-документ).
- Операции: список (фильтр по типу, поиск), добавить, задать canonical,
  добавить/убрать форму и алиас, сменить тип, **объединить дубли** (merge по
  ULID), удалить; показать, где сущность встречается (список документов).
- Вкладка **«Связи»**: рёбра сущности (`works_at`, `member_of`, `role_in`,
  `alias_of`) — добавить/убрать; видеть выведенные `co_occurs` отдельно.
- Хранилище: `entitiesIndexStore` (zustand) поверх `entities.jsonl` +
  `relations.jsonl`; запись атомарная, кэш `ensureEntitiesIndex` инвалидируется.

### T6-3. Runtime-подсветка из справочника

- Новое расширение-декорация (рядом с `vasEntityExtension.ts`): вхождения
  форм справочника подсвечиваются с бейджем типа; переключатель «показать
  сущности» (по умолчанию в режиме просмотра, в разметке — выключен).
- Матчер: `matchEntityEntry` + `expandEntityForms` (склонения); только формы
  ≥3 символов и с границами слова; индекс форм → один regex, кэш на документ.
- **Неоднозначные формы** (одна форма → несколько ULID) подсвечиваются иначе
  (двойной бейдж / «неоднозначно») — сигнал для панели конфликтов.

### T6-4. NER-подсказки → в справочник

- У каждого NER-предложения — действие **«В справочник»** (тип + canonical +
  форма), документ не меняется; «Разметить» (чип) остаётся отдельным действием.
- Новая сущность = новый ULID; существующая форма → предложение привязать к
  существующей записи (тот же ULID).
- Для однофамильцев: предложение создать **вторую** запись + связь
  (`works_at` и т.д.) вместо присоединения к первой.

### T6-5. Разрешение конфликтов и материализация якорей

- Панель конфликтов: «Иванов Иван Иванович» встречается в N документов, в
  справочнике 2 кандидата → показать карточки кандидатов + их связи; выбор →
  (а) записать связь, (б) поставить якорь (чип) в конкретные вхождения.
- Автоматический режим: якоря ставятся сами, где разрешение однозначно по
  связям, а форма неоднозначна.
- Разрешение однофамильцев по контексту (см. раздел выше) — общий движок,
  используемый и подсветкой, и маскированием.

### T6-6. Переосмысление re-markup

- Секция «Репозиторий» в NER-дропдауне становится сверкой **справочник ↔
  тексты**:
  - «в текстах, но не в справочнике» — кандидаты на добавление;
  - «в справочнике, но не встречается» — неиспользуемые;
  - «одна форма → несколько сущностей» — неоднозначные (с переходом в
    разрешение конфликтов);
  - конфликты типов по чипам — остаются (T3e).
- Бывшие «changed/missing» по чипам — остаются, но вторичны.

### T6-7. Миграция текущего состояния

- Кнопка «Пересобрать справочник из разметки» уже есть (`rebuildIndex`) —
  дополнить: разносить `forms` (наблюдаемые) и ручные `aliases`.
- Собрать профиль совместных появлений (`co_occurs`) по репо — база для
  разрешения однофамильцев без ручных связей.
- Дубль «Ивановым И. И.» в `lm_hrdo_2` — разобрать через слияние (T6-2).

### T6-8. Правило использования чипа (документация в UI)

- Чип ставится, когда: (а) одна форма = разные сущности; (б) сущность связывает
  несколько документов; (в) нужен якорь для маскирования/аудита; (г) явное
  требование пользователя к стабильной ссылке.
- После T6-5 часть случаев (а) закрывается автоматически — чип материализуется
  по решению конфликта.

### T6-9. Правила-детекторы как данные (корпус guardrails)

- Формат правила — как в guardrails (YAML, `rule_id`/`regex`/`capture_groups`/
  `min_length`/`keywords`/`banlist`/`entropy`/`validators`/`masking.placeholder`);
  правила живут в `harness.yaml` (per-repo) или в каталоге правил рядом со
  справочником — на выбор пользователя.
- Конвертация корпуса: `(?i)` → флаг `i`; `(?-i:…)` → отдельное правило;
  lookaround отсутствует → правок regex не нужно.
- Валидаторы (Luhn, СНИЛС, ИНН, ОГРН, ОГРНИП, IBAN) — чистые функции TS.
- `capture_groups` — семантический span; `min_length` + валидатор отбрасывают
  кандидат целиком (вместо ручного срезания пунктуации).
- Union-span при пересечении правил (в `mergeSpans`).
- Keyword-gated fallback: для «структурных» типов второе, ослабленное правило
  с обязательным контекстным словом (целое слово, ≤N filler-слов).
- Резерв алиасов, присутствующих в тексте (не переписывать ручные `[[VAS_…]]`).
- Толерантный к дрейфу регекс алиаса в `unmaskText`.
- Fail-open: исключение правила → «правило не применилось», текст не меняется.
- Регрессионный корпус из guardrails → vitest-файл с позитивными/негативными
  кейсами (источник FP-примеров: «Общество Ромашка Москва открыло филиал»,
  «Красная Площадь закрыта сегодня» и т.п.).

## Риски

1. **Ложные срабатывания подсветки** (короткие формы, подстроки, имена
   «Москва»/«Иван»). Лечится: порог длины, границы слова, только формы
   справочника, выключатель.
2. **Наполнение справочника мусором** при агрессивном NER. Лечится: в справочник
   попадает только подтверждённое пользователем.
3. **Производительность**: репо с тысячами документов × формы справочника —
   нужен кэш и ленивая загрузка форм по открытым документам.
4. **Семантика `canonical`**: сейчас canonical = первая форма; переход на
   явное поле меняет поведение матчинга — мигрировать мягко (при отсутствии
   явного canonical брать текущее значение).
5. **Ошибочная связь → тихая подмена сущности**: если связь `works_at` задана
   неверно, однофамилец будет разрешаться не туда, и это не заметно. Лечится:
   связи из UI — явные и отменяемые; выведенные (`co_occurs`) — только
   предложения, не применяются молча; при смене текста якорь чипа сохраняет
   разрешение и делает его явным.
6. **Разрешение по контексту хрупко**: контекст (абзац) может измениться, и
   разрешение поменяется. Поэтому после разрешения конфликта — якорь в
   документе (T6-5) как закрепление решения.
7. **Регулярки из корпуса guardrails — RE2-семантика**: инлайн-флаги `(?i)` и
