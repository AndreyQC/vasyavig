# Design

## Context

`src-tauri/Cargo.toml:28` подключает anydoc абсолютным путём
`path = "C:/repos/github/anydoc"`. Источник — клон `firecrawl/anydoc` на
коммите v0.2.3 (`bf3d33e`) с локальной веткой `feat/to-markdown-with-assets`
(2 коммита, ~135 строк): единственная используемая приложением функция
`anydoc::to_markdown_with_assets` (`src-tauri/src/commands/convert.rs:15`)
опирается на приватные внутренности крейта (`render::markdown`), поэтому
заменить можно только крейт целиком, а не надстроиться поверх crates.io-версии.
Мотивация — в proposal.md (Why).

У vasyavig нет внешних пользователей API; страдают только разработчики,
клонирующие репозиторий. CI-воркфлоузов в репо нет. Текущий git-пак — 1.53 MiB.

## Goals / Non-Goals

**Goals:**

- Сборка из чистого клона на любой машине без подготовки вне репозитория.
- Сохранение поведения конвертации байт-в-байт (тот же Rust-код).
- Лицензионная чистота и прослеживаемость происхождения вендоренной копии.

**Non-Goals:**

- Не переносим тесты/фикстуры anydoc (2.1 МБ) — разработка форка остаётся в
  локальном клоне `C:/repos/github/anydoc`.
- Не вендорим node/python/wasm-биндинги anydoc, bench, fuzz, examples (кроме
  обязательного по `include` `examples/convert.rs`).
- Не делаем PR в апстрим в этом change (возможный будущий трек — см. proposal).
- Не автоматизируем синхронизацию форка скриптом (ручная процедура в
  PROVENANCE.md; автоматизируем, если станет рутиной).

## Decisions

### D1. Вендоринг копией крейта + относительная path-зависимость

Выбрано: каталог `vendor/anydoc/` в корне репо, зависимость
`anydoc = { path = "../vendor/anydoc" }`.

Альтернативы:

| Вариант | Почему нет |
|---|---|
| git-зависимость от личного форка на GitHub | требует вечного публичного хостинга форка + сеть при первой сборке; не «внутри репозитория» |
| публикация форка на crates.io под новым именем | бремя поддержки крейта-дубликата; внешнее состояние остаётся |
| git submodule | классические грабли DX (забытый `--recursive`, неочевидная диагностика) |
| PR в апстрим и ждать релиза | лучший финал, но таймлайн не наш; совместим с вендорингом как промежуточным шагом |

### D2. Состав вендора — минимальный пакет крейта

Копируем ровно то, что крейт сам считает пакетом (поле `include` его
Cargo.toml): `src/` (76 файлов, ~1.1 МБ, без фикстур), `examples/convert.rs`,
`README.md`, `LICENSE` (MIT) — плюс наш `PROVENANCE.md`. Из копии `Cargo.toml`
удаляется ТОЛЬКО секция `[workspace]` (её members `node`/`python`/`wasm` не
вендорятся — cargo упадёт на ненайденных членах). Остальное (edition 2024,
rust-version 1.88, `[dev-dependencies]`, `[profile.release]`) сохраняем как в
оригинале — минимальная дельта упрощает будущие обновления копии. Предупреждение
про игнорируемый profile у не-корневого пакета безвредно.

Требование к тулчейну не растёт: README уже требует Rust 1.90+ > 1.88.

### D3. Расположение `vendor/anydoc` в корне репозитория

Отдельно от `src-tauri/`: сторонний код виден на верхнем уровне, путь из
`src-tauri/Cargo.toml` — `../vendor/anydoc`. Workspace-осложнений нет: у
`src-tauri` нет секции `[workspace]`, авто-включения члена не происходит,
`exclude` не нужен.

### D4. Источник истины и процедура обновления

Сборка ВСЕГДА использует `vendor/anydoc` — даже на машине автора. Правки anydoc
ведутся в локальном форке (там тесты и фикстуры), затем переносятся в vendor
по процедуре из `PROVENANCE.md`: скопировать `src/`, восстановить правку
`Cargo.toml` (без `[workspace]`), обновить записи PROVENANCE, при смене
зависимостей перегенерировать `Cargo.lock`. PROVENANCE фиксирует базовые
коммиты, поэтому дрейф обнаруживается сравнением с `git log` форка.

### D5. Проверка «чистого клона» на машине автора

Временно переименовать `C:/repos/github/anydoc` и выполнить сборку — если
проект собирается, абсолютная зависимость действительно ушла. Дешёвая
имитация «чужой» машины без второго компьютера.

## Risks / Trade-offs

- [Дрейф форк ↔ vendor: правка осталась только в форке] → сборка всегда из
  vendor (D4), расхождение видно по PROVENANCE-коммитам.
- [Регрессия в anydoc остаётся незамеченной: интеграционных тестов конвертации
  в репо нет] → inline-тесты в `src/` вендорятся и запускаются
  (`cd vendor/anydoc && cargo test`); ручная проверка конвертации .docx из
  задач.
- [Апстрим-фиксы (в т.ч. security) не подхватываются автоматически] →
  осознанный trade-off; процедура re-vendor в PROVENANCE; финальное решение —
  PR в апстрим и возврат на crates.io.
- [Рост репозитория ~0.5 MiB в паке] → приемлемо против полностью сломанной
  сборки у других.

## Migration Plan

Применение: задачи из tasks.md; откат — один коммит (вернуть
`path = "C:/repos/github/anydoc"`, удалить `vendor/`, восстановить lock).
Внешних интерфейсов change не меняет.
