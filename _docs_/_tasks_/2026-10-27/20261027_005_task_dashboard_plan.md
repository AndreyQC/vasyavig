## 2. Данные: два уровня и сменный источник

**D1 — кандидаты из реестра.** Задачные документы находим в `documents.jsonl`,
дерево файлов не сканируем: реестр уже загружен в `harnessStore`, кандидаты —
производная коллекция его записей.

**Факт (скан реестра `lm_hrdo_2`, 1788 записей, 2026-10-27).** Типа `task` в
реестре НЕТ. Файлы с task-yaml (861) распределяются по `kind` → типу реестра:
`backlog → backlog` (49), `external-tracker-task → tracker` (38),
`internal-task → tracker/analysis` (3), `daily-task → plan/result/...` (762,
документы процесса). Статусы из конвертов после нормализации:
пусто (402), `done` (368), `open` (69), `cancelled` (14), `in_progress` (8).

**D4 — критерий отбора кандидатов.** Фильтр реестра по `type` из константы
`TASK_TYPES`, регистронезависимо. Дефолт — `["tracker", "backlog"]` (по
факту: типы, действительно несущие задачи); набор расширяется одной
константой, позже — манифестом (§3). Daily-task в `plan`/`result` в v1
не показываются (заглушили бы дашборд процессными документами).

**D2 — подробности из файлов.** Для каждого кандидата читаем шапку файла
(достаточно первых ~4 КБ) и парсим task-yaml конверт. Статус всегда живой,
из файла (критерий приёмки roadmap). Кандидат без task-yaml в файле из
списка исключается. Значения нормализуются: трим, срез кавычек, срез
инлайн-комментария ` # …` (в примере встречаются: `status: open # open |
in_progress | done | cancelled`), приведение статуса к канону по алиасам
словаря (§3): `Выполнена/finalized → done`, `В работе/active → in_progress`,
`Открыта → open`. Неизвестное значение показывается «как есть», нейтральным
цветом.

**D3 — сменный источник.** Требование пользователя: инструмент легко
переключается; впоследствии на БД переедет и сам индекс. Доступ к данным —
через узкий интерфейс в `src/lib/harnessTasks.ts`:

```ts
interface TaskSource {
  /** Кандидаты: задачные документы репозитория (сейчас — фильтр реестра). */
  listTaskDocs(repoRoot: string): Promise<TaskDocRef[]>;
  /** Подробности task-yaml документа (сейчас — чтение шапки файла). */
  loadTaskDetails(repoRoot: string, ref: TaskDocRef): Promise<TaskDetails | null>;
}
```

Сейчас — реализация `IndexTaskSource` (реестр + шапки файлов). Позже —
`DbTaskSource` без изменений UI и стора: UI/стор знают только интерфейс.

**D5 — парсер task-yaml.** Новый `parseTaskEnvelope`: маркеры
`<!-- [<[task-yaml]]` … `[[task-yaml]>] -->`, тот же плоский YAML-парсер
(выделить общий разбор полей из `parseHarnessEnvelope`). Окно поиска — 30
строк: в примере task-yaml стоит после harness-конверта и закладки (~строка
10). Сам `parseHarnessEnvelope` не меняется (семантика 1:1 с
harness_yaml.py, окно 5 строк) — регресс round-trip тестов. Маркер закрытия
именно `[[task-yaml]>]` (не `[[task-yaml]]>`) — как в `HIDDEN_ENVELOPE_RE`.

## 3. Манифест проекта («визитная карточка», создан)

Манифест лежит **в корне** harness-репозитория: `harness_manifest.json`
(решение пользователя: корень вместо `_docs_`, snake_case по конвенции
репозиториев). Файл создан и закоммичен в `lm_hrdo_2` (`cd34e2d5`, ветка
`dev`). Vasyavig читает словарь из манифеста уже в этой задаче (расширение
скоупа по просьбе пользователя); при отсутствии/повреждении манифеста —
встроенный дефолт. Форма:

```jsonc
{
  "manifest": 1,                    // версия схемы
  "kind": "harness",                // маркер вида репозитория
  "name": "LM.HRDO-2",
  "vocabularies": {
    "task": {
      // типы реестра, считающиеся задачами (критерий отбора D4)
      "types": ["tracker", "backlog"],
      // справочник kind для фильтра в UI
      "kinds": ["daily-task", "backlog", "external-tracker-task", "internal-task"],
      // словарь статусов: канон + алиасы (нормализация D2) + цвет бейджа
      "statuses": [
        {"value": "open",        "label": {"ru": "Открыта",   "en": "Open"},        "color": "blue",   "aliases": ["Открыта"]},
        {"value": "in_progress", "label": {"ru": "В работе",  "en": "In progress"}, "color": "orange", "aliases": ["В работе", "active"]},
        {"value": "done",        "label": {"ru": "Выполнена", "en": "Done"},        "color": "green",  "aliases": ["Выполнена", "finalized"]},
        {"value": "cancelled",   "label": {"ru": "Отменена",  "en": "Cancelled"},   "color": "gray",   "aliases": []}
      ]
    }
  }
}
```

- Предикат harness-репо (D8): манифест (валидный JSON-объект) ИЛИ реестр;
  битый манифест не считается визитной карточкой. Словарь задач (§ ниже) —
  из манифеста, дефолт — значения выше, по факту скана реестра.
- Генерация/валидация манифеста тулингом harness-репо (`make ...`) — вне
  скоупа Vasyavig, отдельная работа в harness-репо.

## 4. Кэш и обновление

- Кандидаты пересчитываются от `harnessStore.indexes` + `version`:
  перезагрузка реестра (watcher по `documents.jsonl`) автоматически обновляет
  список.
- Подробности — кэш в новом сторе `harnessTasksStore` по нормализованному
  пути файла; инвалидация — watcher-событие `.md` внутри harness-корня
  (дебаунс 300 мс на корень уже есть в `useFileWatcher`) → перечитать шапку
  одного файла; событие `documents.jsonl` → сброс слияния (ulid/пути могли
  измениться).
- Чтение шапок — ленивое, при первом открытии дашборда; файлы читаются
  параллельно с ограничением; индикатор загрузки.

## 5. UI дашборда

- Точка входа — кнопка «Задачи» в `SidebarHeader` (видна, если среди корней
  есть harness-репо — по флагу из §7).
- Носитель — переключаемый режим сайдбара «дерево ↔ задачи» (панель той же
  ширины; не модалка и не поповер). Сверху — селектор harness-корня (если их
  несколько), строка фильтров, список.
- Строка: бейдж статуса (канон словаря — цветной, пусто/неизвестное —
  нейтральный), `kind`, `title` из реестра (или task-id + имя файла),
  `assignee`, относительный путь.
- Фильтры: status / kind / assignee (select из значений списка), текстовый
  поиск по title/task/path. Сортировка: `updated` (реестр) по убыванию, затем
  `title`.
- Клик по строке — `openFile(normalizeJoin(repoRoot, path))` — тот же
  переход, что у ULID-ссылок.
- Пустое состояние: «task-yaml документы не найдены» + подсказка
  (`make doc-id` / `make doc-index` в harness-репо).

## 7. Значок harness-корня

**D8 — единый предикат.** «Это harness-репо» — одна функция в
`src/lib/harnessIndex.ts` (рядом с `findHarnessIndex`). Сейчас: существует
`<dir>/_docs_/_index/documents.jsonl`. Когда в репо появится манифест (§3) —
предикат расширяется (манифест || реестр), затем переносится на манифест, в
одном месте; потребители не меняются.

**D9 — корень-репо и корень-родитель.** Флаг считается true, если:
(a) предикат сработал прямо для корня — проба при `addRoot`/
`restoreLastWorkspace`/`openWorkspaceFile`/`refreshRoot`; (b) реестр найден
в поддереве уже загруженного корня («каталог, который содержит в себе
репозиторий») — вывод из `fileStore.trees` без новых чтений диска, пересчёт
при обновлении дерева.

**D10 — где показан (Q1, принято).** Значок в заголовке секции корня
(`RootSection`, рядом с именем, tooltip «harness-репозиторий») и мини-значок
на вкладках файлов этого репо (`EditorTabs`). Иконка — константа
`HARNESS_ICON` (из `@gravity-ui/icons`, кандидат `Boxes`), одна на оба места,
замена — одна строка.

**D11 — сериализация.** Флаг производный: `serializeWorkspace` пишет только
`path`/`color` — workspace-файл не меняется; тест на регресс.
