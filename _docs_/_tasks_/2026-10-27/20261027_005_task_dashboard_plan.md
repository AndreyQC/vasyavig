## 1. Цель и границы

**Цель.**

1. Дашборд задач (roadmap, задача 6): список задачных документов с полями
   task-yaml (`kind/status/task/tracker/priority/assignee`), фильтры, переход
   к документу.
2. Значок harness-репозитория: при открытии каталога, который является или

   специальным значком секцию корня в сайдбаре и вкладки файлов этого репо.

**Не входит:** задача 5 (граф/дерево документов), задача 7 (write-path),

Порядок 5/6: дашборд делается первым (выбор пользователя); `TaskSource` и
словарь статусов лягут в основу графа документов (задача 5).

## 2. Данные: два уровня и сменный источник

**D1 — кандидаты из реестра.** Задачные документы находим в `documents.jsonl`
по `type` (фильтр «task-типов», D4). Дерево файлов не сканируем: реестр уже
загружен в `harnessStore`, кандидаты — производная коллекция его записей.

**D2 — подробности из файлов.** Для каждого кандидата читаем шапку файла
(достаточно первых ~4 КБ) и парсим task-yaml конверт. Статус всегда живой,
из файла (критерий приёмки roadmap: «статус соответствует task-yaml»).
Кандидат, в файле которого task-yaml нет, из списка исключается: реестровый
фильтр — только отбор кандидатов.

**D3 — сменный источник.** Требование пользователя: инструмент легко
переключается, впоследствии на БД переедет и сам индекс. Доступ к данным —
через узкий интерфейс в `src/lib/harnessTasks.ts`:

```ts
interface TaskSource {
  /** Кандидаты: задачные документы репозитория (сейчас — фильтр реестра). */
  listTaskDocs(repoRoot: string): Promise<TaskDocRef[]>;
  /** Подробности task-yaml документа (сейчас — чтение шапки файла). */
  loadTaskDetails(repoRoot: string, ref: TaskDocRef): Promise<TaskDetails | null>;
}
```

Сейчас — реализация `IndexTaskSource` (реестр + шапки файлов). Позже —
`DbTaskSource` без изменений UI и стора: UI/стор знают только интерфейс.

**D4 — task-типы реестра.** Фильтр `type` — регистронезависимое сравнение;
базовый набор `["task"]` (константа, расширяемая). Точный набор типов
примера сверить по его реестру при реализации (Q2).

**D5 — парсер task-yaml.** Новый `parseTaskEnvelope`: те же маркеры с именем
`task-yaml`, тот же плоский YAML-парсер (выделить общий разбор полей из
`parseHarnessEnvelope`). Окно поиска — 30 строк: в примере task-yaml стоит
после harness-конверта и закладки (~строка 10). Сам `parseHarnessEnvelope`
не меняется (семантика 1:1 с harness_yaml.py, окно 5 строк) — регресс
round-trip тестов.

## 3. Кэш и обновление

- Кандидаты пересчитываются от `harnessStore.indexes` + `version`:
  перезагрузка реестра (watcher по `documents.jsonl`) автоматически обновляет
  список.
- Подробности — кэш в новом сторе `harnessTasksStore` по нормализованному
  пути файла; инвалидация — watcher-событие `.md` внутри harness-корня
  (дебаунс 300 мс на корень уже есть в `useFileWatcher`) → перечитать шапку
  одного файла; событие `documents.jsonl` → сброс слияния (ulid/пути могли
  измениться).
- Чтение шапок — ленивое, при первом открытии дашборда; файлы читаются
  параллельно с ограничением; индикатор загрузки.

## 4. UI дашборда

- Точка входа — кнопка «Задачи» в `SidebarHeader` (видна, если среди корней
  есть harness-репо — по флагу из §6).
- Носитель — переключаемый режим сайдбара «дерево ↔ задачи» (панель той же
  ширины; не модалка и не поповер). Сверху — селектор harness-корня (если их
  несколько), строка фильтров, список.
- Строка: бейдж статуса (известные статусы — цветные, прочие — нейтральные),
  `kind`, `title` из реестра (или task-id + имя файла), `assignee`,
  относительный путь.
- Фильтры: status / kind / assignee (select из значений списка), текстовый
  поиск по title/task/path. Сортировка: `updated` (реестр) по убыванию, затем
  `title`.
- Клик по строке — `openFile(normalizeJoin(repoRoot, path))` — тот же
  переход, что у ULID-ссылок.
- Пустое состояние: «task-yaml документы не найдены» + подсказка
  (`make doc-id` / `make doc-index` в harness-репо).

## 6. Значок harness-корня

**D8 — единый предикат.** «Это harness-репо» — одна функция в
`src/lib/harnessIndex.ts` (рядом с `findHarnessIndex`). Сейчас: существует
`<dir>/_docs_/_index/documents.jsonl`. Позже в репо появится манифест-файл
(«визитная карточка» репозитория такого вида, требование пользователя) —
предикат расширяется (манифест || реестр) в одном месте, потребители не
меняются.

**D9 — корень-репо и корень-родитель.** Флаг считается true, если:
(a) предикат сработал прямо для корня — проба при `addRoot`/
`restoreLastWorkspace`/`openWorkspaceFile`/`refreshRoot`; (b) реестр найден
в поддереве уже загруженного корня («каталог, который содержит в себе
репозиторий») — вывод из `fileStore.trees` без новых чтений диска, пересчёт
при обновлении дерева.

**D10 — где показан.** Значок в заголовке секции корня (`RootSection`, рядом
с именем, tooltip «harness-репозиторий») и мини-значок на вкладках файлов
этого репо (`EditorTabs`) — трактовка слова «вкладка» (Q1). Иконка — из
`@gravity-ui/icons` (кандидат `Boxes`/`Layers`, финал на реализации), единая
для обоих мест.

**D11 — сериализация.** Флаг производный: `serializeWorkspace` пишет только
`path`/`color` — workspace-файл не меняется; тест на регресс.

## 8. Риски

| Риск | Митигация |
|---|---|
| Много кандидатов → медленное чтение шапок | читать ~4 КБ, лениво при открытии дашборда, параллельно с ограничением, кэш |
| task-yaml дальше 30 строк — не найден | эталонный формат — шапка файла; ограничение задокументировано |
| watcher-шторм (git pull, make doc-index) | дебаунс на корень уже есть; сброс только затронутых записей |
| Тип «task» в реестре не совпадает с фактическим | D4: набор типов — константа; сверить по реестру примера (Q2) |
| Реестра нет/устарел (не запущен `make doc-index`) | пустое состояние с подсказкой; статусы всё равно из файлов |
| Флаг попадёт в workspace-файл | D11 + тест сериализации |
