**Дата:** 2026-10-27
**Статус:** решение принято и реализовано (`989ca86`)
**Фаза:** Phase 7 — Harness, уточнение задачи 3.1

## 1. Причина

Схема `ulid:` слишком общая: по grep `](ulid:` легко спутать с другими
идентификаторами/текстом, а слово `ulid` встречается в конвертах, закладках и
`related`/`based_on`. Нужен однозначный маркер, по которому поиск сразу
отличает ссылку от прочих упоминаний.

## 2. Решение

- **Пишем:** `[<имя файла>](harness-ulid:<ULID>)`,
  якорь — `harness-ulid:<docULID>#<anchorULID>`.
- **Читаем:** legacy `harness_ulid:` (промежуточный вариант, жил несколько
  минут 2026-10-27) и `ulid:` (исходный формат). Миграция не нужна;
  `buildUlidHref` всегда пишет `harness-ulid:`.
- Поиск: `harness-ulid:` — ровно один токен, не пересекается с конвертами
  (`id: 01…`), закладкой (`` `01…` ``) и списками связей.

## 3. Сравнение вариантов (прототип 2026-10-27)

| Проверка | `harness_ulid:` | `harness-ulid:` |
|---|---|---|
| RFC 3986 | невалидная (подчёркивание запрещено) | **валидная** |
| transform по умолчанию | href сохраняется как относительный путь | href вырезается (нужен `allowedSchemes`) |
| DOMPurify по умолчанию | проходит по fallback | вырезается (нужен `ALLOWED_URI_REGEXP`) |
| transform/DOMPurify с allow-list | работает | работает |
| WYSIWYG parse -> serialize | дословно | дословно |
| grep-однозначность | да | да |

**Почему выбрана валидная схема.** Поведение `harness_ulid:` было
случайным: `sanitize-html` не видел в ней схему и пропускал как относительный
путь. Валидная `harness-ulid:` распознаётся всеми парсерами предсказуемо и
fail-closed: если новый путь рендера забудет allow-list, ссылка станет текстом
(видно), а не странным относительным URL. Конфигурация уже задана и покрыта
тестами.

## 6. Ограничения

- Схема не зарегистрирована в IANA: вне Vasyavig клика не будет (U2), но
  синтаксически href валиден.
- Legacy `harness_ulid:`/`ulid:` поддерживаются бессрочно на чтение; новых
  ссылок с ними приложение не создаёт.
- Автодополнение/вставка — отдельная задача.
