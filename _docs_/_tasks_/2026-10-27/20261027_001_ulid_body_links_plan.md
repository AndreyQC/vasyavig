## 3. Вопросы исследования

### Q1. Формат ссылки в теле

**Требование пользователя (2026-10-27, бизнес-сценарий).** Нужна структура,
похожая на ссылку: в тексте видно имя файла-цели, ULID хранится машинно, в
просмотре через приложение ссылка кликабельна. После уточнений (U1-U3) лишние
поля в тексте не храним: имя файла + `ulid:` в href достаточно, остальное
подтягивается из реестра по ULID.

Варианты:

| # | Формат | Пример |
|---|---|---|
| A | голый ULID (как сейчас) | `см. 01M5B8R7MQJZKD1NMQ7M9KZ1F0` |
| B | ULID в инлайн-коде | ``см. `01M5B8R7MQJZKD1NMQ7M9KZ1F0` `` |
| C | markdown-ссылка со схемой | `[20261027_001_ulid_body_links_plan.md](ulid:01M5B8R7MQJZKD1NMQ7M9KZ1F0)` |
| D | markdown-ссылка на ULID как URL | `[Имя файла](01M5B8R7MQJZKD1NMQ7M9KZ1F0)` |
| E | YFM-спецсинтаксис (если поддерживается установленными версиями) | уточнить по `@diplodoc/transform` 4.77 / `@gravity-ui/markdown-editor` 15.44 |
| F | markdown-ссылка + метаданные в `title` | `[Имя файла](ulid:01M… "type: plan")` — отвергнут по U1 |

**Принято предварительно (U1-U3): C** — `[<имя файла>](ulid:<ULID>)`.
Метаданные (title/type/project/путь/даты/связи) в тексте не дублируются:
приложение резолвит ULID по реестру и показывает их в плашечке (Q3).
Вариант F оставлен в таблице как отвергнутый: дублирование полей устаревает.
Проверить в исследовании: round-trip, экранирование, поведение `Link`-ноды
Gravity, читаемость в `git diff`.

Критерии выбора: round-trip WYSIWYG <-> Markup <-> save без потерь; читаемость
в plain markdown и `git diff`; совместимость со старыми 1181 файлами (без
миграции); не конфликтует с закладкой `doc-check`; сложность реализации в
редакторе и превью; возможность автодополнения и плашечки.
Работа вне Vasyavig — не критерий (U2).

### Q2. Вставка и автодополнение

- Достаточно ли ручного копирования ULID, или нужен поиск по реестру
  (`title`/`project`/`type`) в момент вставки?
- Где вставлять: WYSIWYG, Markup, оба; горячая клавиша или кнопка тулбара.
- При вставке: писать `[<имя файла>](ulid:<ULID>)` целиком (U1) или только
  ULID? Имя файла берётся из реестра (`entry.path` -> basename) на момент
  вставки; расхождение с реестром позже — вопрос Q3.
- Минимальный объём для задачи 4, чтобы не тащить UI-пикер в Markup.

### Q3. Отображение и плашечка

- Видимый текст — имя файла (U3). Внутри приложения ссылка оформлена как
  ссылка (цвет/подчёркивание), клик открывает документ.
- При наведении — плашечка с подробностями из реестра: `title`, `type`,
  `project`, путь от корня, `created`/`updated`, `related`/`based_on`
  (имена, не только ULID), кнопки «Открыть», «Связи».
- Реализация: нативный `title` (многострочный, но с задержкой ОС и без кнопок)
  против кастомного popover (`Popover`/`Tooltip` Gravity): задержка появления,
  позиционирование, доступность с клавиатуры, закрытие по Esc.
- Превью — DOM-элемент ссылки; WYSIWYG — inline-декорация или `Link`-нода.
- Расхождение «имя файла в тексте» vs «актуальные данные реестра»
  (переименование, смена типа): как показывать — тултип, пометка, ничего.

### Q4. Неизвестный и неоднозначный ULID

- Текущее: `ulid-unknown` (пунктир без перехода), `ambiguous` — без перехода.
- Нужно ли: toast с подсказкой («реестр устарел, выполните `doc-index`»),
  отдельная иконка, запрет автодополнения несуществующих id.
- Поведение при `found`, но файла нет на диске (сейчас — toast).
- Плашечка для неизвестного ULID: что показывать вместо метаданных.

### Q5. Границы линкификации

- Не линкифицировать: скрытый конверт, закладку, `related`/`based_on`,
  содержимое код-блоков (проверить: `isTextblock` включает `code_block` —
  сейчас ULID в коде, вероятно, подсвечивается), URL и существующие ссылки.
- Ложные срабатывания: 26-символьные хеши/токены — достаточно ли фильтра
  таймстемпа, нужен ли контекст (`doc:`-префикс, бэктики).
- Совместимость с YFM-разметкой (`{% note %}`, таблицы, вставки).
- Не перехватывать обычные ссылки: `ulid:` — отдельная схема, `<a href>` с
  http/https/относительным путём остаются штатными.

### Q6. Совместимость с harness-инструментами

- `make doc-check` / `doc-index` / `doc-find`: что сломается при выборе
  markdown-ссылки (закладка, frontmatter, regex)?
- Обратная совместимость: старые документы с голым ULID должны продолжать
  работать без миграции; новый формат — opt-in.
- **Внешний вид вне Vasyavig — не требование (U2).** Достаточно, чтобы
  markdown оставался читаемым: `ulid:`-ссылка в GitHub/Gramax покажет текст
  без перехода; специально поддерживать относительные пути не нужно.

### Q7. Round-trip и сериализация

- Для каждого варианта Q1: WYSIWYG -> Markup -> save, повторный проход —
  идемпотентность.
- Риски: `normalizeLink` (уже отключён в `src/lib/preserveUrlsExtension.ts`),
  экранирование, автолинки, YFM-нормализация, поведение `Link`-ноды Gravity.
- Проверять на фикстурах `src/lib/harnessRoundTrip.test.ts` и
  `harnessRoundTripYfm.test.ts` (238 тестов — базовая линия).

### Q8. Производительность автодополнения

- 1765 записей: поиск по подстроке на каждый keystroke или предварительный
  индекс (по title/project/type)?
- Паттерн UI: `Suggest`/`Autocomplete` Gravity для WYSIWYG; completion
  CodeMirror для Markup (задача 4).
- Кэш реестра уже есть (`harnessStore`), вопрос — стоимость фильтрации.

### Q9. Якоря внутри документа (идея пользователя U4)

Цель: пометить конкретное место в документе собственным ULID и типом `anchor`,
чтобы ссылаться на него и перепрыгивать сразу к месту (устойчиво к правкам
текста, в отличие от номера строки или текста заголовка).

- **Синтаксис маркера** — сравнить три варианта:
  - A. скрытый конверт-комментарий (как harness-yaml): `<!-- [<[anchor]] … -->`
    — не видно в рендере, но легко удалить Ctrl+A; нужно уметь находить место
    для скролла (ближайший следующий блок/заголовок).
  - B. видимая метка-блок: отдельная строка/бейдж `[anchor: <ULID>]` или
    `` `#<ULID>` `` — видно и можно кликнуть, но засоряет текст.
  - C. ULID на заголовке: `## Раздел {#<ULID>}` — семантично, но требует
    поддержки атрибутов заголовка в Gravity/YFM (проверить).
- **Формат ссылки на якорь**: `[имя файла](ulid:<docULID>#<anchorULID>)`.
  Альтернатива — `ulid:<anchorULID>` с поиском по всем документам (дорого,
  и ULID якоря не говорит, где он).
- **Обнаружение**: сканирование открытого документа (маркер + контекст) против
  записи в `documents.jsonl` (`type: anchor`, `path#anchor`). Реестр Vasyavig
  только читает — запись якорей означала бы write-path (задача 7) или
  пересборку `doc-index` в harness-репо.
- **UX**: команда «Вставить якорь» (генерирует ULID, ставит маркер), список
  якорей документа при автодополнении ссылки, переход + подсветка места,
  что показывать в плашечке для ссылки на якорь.
- **Ограничения**: дубли ULID, якорь без ссылок, `doc-check` про якоря не
  знает, round-trip маркера, поведение при удалении/переносе блока.
- **Итог исследования**: зафиксировать концепцию и синтаксис; реализация —
  отдельная задача (кандидат в Phase 8), не в этой.
