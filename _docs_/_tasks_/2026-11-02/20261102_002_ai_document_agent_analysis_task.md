## 2. Как поняты корректировки (restatement)

1. **Модель не локальная, а в периметре.** В настройках приложения нет
   локального рантайма, скачивания весов и выбора «локальная/внешняя».
   Есть endpoint модели в периметре и доступ к нему по
   **OpenAI-совместимому протоколу** (base URL, модель, авторизация,
   `/v1/chat/completions`, при наличии — стриминг и JSON mode).
2. **Запись файлов нужна.** Ассистент должен не только предлагать diff, но
   и уметь реально править markdown (и другие текстовые документы) — иначе
   сценарий «поправить документ» не закрывается.
3. **Но запись — только строго описанными инструментами.** Никаких
   `run_command`, shell, произвольных исполняемых команд, generic
   `write_file(path)` и произвольной файловой системы. Каждый инструмент
   имеет фиксированную схему, область действия, лимиты и проверки.
4. **Остальное из исходной идеи — гипотезы для проверки:** двухуровневость
   (быстрый/сильный), эскалация, proposals/diff, ограничение инструментов
   по тирам, audit. Часть уже уточнена решениями ниже (ручное переключение
   моделей, без автоматической эскалации); остальное надо пересобрать под
   модель в периметре и под разрешённую запись.
5. **Срок — сегодня.** Нужен анализ и рекомендация: делать/не делать, в
   каком объёме и в каком порядке.
6. **Запись — сначала в редактор (dirty).** Агент меняет буфер открытого
   документа; вкладка становится dirty, работает undo. На диск сохраняет
   пользователь (Ctrl+S / «Сохранить всё»). Агент не вызывает save и не
   делает autosave.
7. **MVP-объём записи (решение 2026-11-02):** правка уже открытых
   документов + создание нового документа в открытом корне. Переименование,
   перемещение и удаление — вне MVP.
8. **Все write-операции — через diff и подтверждение (решение 2026-11-02).**
   Никакого auto-apply в MVP: модель предлагает, пользователь нажимает
   «Применить». Это касается replace, insert и create.
9. **Автоматическая эскалация — не в MVP (решение 2026-11-02).** В конфиге
   может быть несколько моделей, переключение — вручную; автоматическая
   эскалация и профили «быстрый/сильный» — отдельные этапы после обкатки
   записи.
10. **Контекст по умолчанию (решение 2026-11-02):** активный документ
    целиком + выделение + результаты детерминированных проверок. В панели
    виден объём контекста; для больших файлов — лимит и чанкование по
    заголовкам.
11. **Размещение (решение 2026-11-02):** сворачиваемая панель справа, не
    отдельная вкладка. На узком окне — overlay; вкладку можно добавить
    позже.
12. **MVP-1 — quick actions + рецепты, без свободного чата (решение
    2026-11-02).** Модель вызывается внутри фиксированного пайплайна;
    свободный чат и tool-loop — MVP-2.
13. **Состав quick actions MVP-1 (решение 2026-11-02):** «Проверка
    документа» (ссылки, якоря, TOC, harness-конверт) и «Письмо HTML».
    Саммари/перевод и черновик harness-документа — позже.
14. **Фокус MVP (решение 2026-11-02):** harness-документация + общие
    markdown-фиксы. Проверка документа и письмо работают везде, но
    приоритет — реестр, граф, конверты, ULID и задачи harness.
15. **Настройки подключения — конфиг-файл с crypto-значениями (решение
    2026-11-02).** Ориентир — реализация в проекте
    `C:\repos\personal\GITHUB\transcript-optimizer`: OpenAI-совместимый
    endpoint, модель, параметры; секреты (`api_key`, при необходимости
    `base_url`) хранятся как `crypto__<ENV>__<ciphertext>` (Fernet), ключ —
    из переменной окружения. Plain-ключи в конфиге не храним. Конфиг можно
    открыть (read-only); изменения — через UI-форму.
16. **Конфиг — общий файл настроек приложения (решение 2026-11-02).** В нём
    несколько OpenAI-совместимых моделей (`llm.models`), `default_model`,
    переключение между моделями во время работы, а также другие настройки
    приложения (app/editor/assistant/files). Формат расширяемый: неизвестные
    секции и ключи сохраняются при записи.
17. **Текущая модель = `default_model` (решение 2026-11-02).** Переключение
    в UI обновляет `default_model` в конфиге; файл перезаписывается с
    сохранением неизвестных ключей.
18. **Состав app-настроек — гибрид (решение 2026-11-02).** В конфиге живут
    `llm`, `assistant`, `editor` и `files`; тема и язык остаются глобальными
    в localStorage. Per-workspace переопределения темы/языка — позже.
19. **Расположение конфига (решение 2026-11-02):** отдельный
    `vasyavig.yaml` рядом с файлом `.vasyavig-workspace`.
    Секреты — только crypto-значения; без env-ключа файл неработоспособен
    даже при передаче третьим лицам.
20. **Редактирование конфига (решение 2026-11-02):** настройки меняются
    через UI-форму приложения; сам `vasyavig.yaml` открывается только для
    просмотра (read-only). Ручные правки — внешним редактором.
21. **Псевдонимизация (идея 2026-11-02):** локальные детекторы + NER
    находят чувствительные сущности, заменяют их стабильными
    плейсхолдерами, после ответа модели значения восстанавливаются.
    Маппинг — только в памяти; модель видит плейсхолдеры, а не значения.
22. **Этапность псевдонимизации (решение 2026-11-02):** в MVP —
    детерминированные детекторы + плейсхолдеры + ручное подтверждение в
    превью; NER (персоны/организации/локации) — после MVP как сменный
    детектор.
23. **Недоступность модели (решение 2026-11-02):** короткий retry (1–2
    попытки на таймаут/5xx), затем понятная ошибка и предложение выбрать
    другую модель из конфига. Автоматического fallback нет;
    детерминированные проверки продолжают работать.
24. **Старт реализации — сразу MVP-1 с моделью (решение 2026-11-02).**
    Отдельный MVP-0 не выделяем: панель, findings, diff/apply, «Письмо
    HTML», provider и рецепт проверки документа входят в первый этап.
25. **Audit — локально, только метаданные (решение 2026-11-02).** Время,
    модель, тип операции, пути документов, hash, результат apply; без
    содержимого документов и без значений сущностей.
26. **Фаза реализации — Phase 8 (решение 2026-11-02).** Старт сразу,

### 3.2. Набор инструментов (read + write)

Нужен полный список с схемами, лимитами и тиром. Набросок для анализа:

| Tool | Тир | Аргументы | Действие / ограничение |
|---|---|---|---|
| `get_active_document` | read | — | Текст, путь, режим, dirty, ULID активной вкладки; лимит размера |
| `get_selection` | read | — | Выделение и позиция курсора |
| `list_open_documents` | read | — | Открытые вкладки, dirty; максимум 50 |
| `list_workspace_roots` | read | — | Opaque `rootId`, псевдоним/имя корня; абсолютные пути модели не отдаются |
| `get_document` | read | `ulid` | Документ из harness-реестра; только реестр |
| `search_documents` | read | `query`, `rootId?`, `limit?` | Лексический поиск по открытым корням; 20 результатов, сниппет 200 символов |
| `get_related_documents` | read | `ulid` | Соседи по графу; максимум 50 |
| `list_tasks` | read | `status?`, `assignee?`, `project?` | Задачи task-yaml; максимум 100 |
| `check_document` | pure | `docId`, `rules?` | Детерминированные проверки: ссылки, якоря, TOC, конверт |
| `propose_replace` | propose | `docId`, `oldText`, `newText`, `expectedCount?` | Замена ровно N вхождений (по умолчанию 1); ошибка, если неоднозначно; diff + подтверждение |
| `propose_insert` | propose | `docId`, `anchor`, `position`, `text` | Вставка блока до/после якоря или в конец; покрывает TOC и добавление в конец; diff + подтверждение |
| `propose_create` | propose | `rootId`, `relativePath`, `content`, `overwrite?` | Только `.md/.yfm/.txt`; путь внутри корня; без overwrite; после apply открывается вкладка dirty. Реализация через существующий file-flow создаёт пустой файл на диске — вариант untitled-вкладки требует отдельного анализа |
| `apply_proposal` | app-only | `proposalId` | Вызывает приложение после подтверждения, не модель |

Все write-инструменты называются `propose_*` и **не меняют буфер**:
модель возвращает предложение, приложение показывает diff и применяет его
только после подтверждения. После применения вкладка становится dirty,
undo работает штатно. `save_document` модели **не даётся**: сохранение на
диск — действие пользователя (Ctrl+S / «Сохранить всё»).

Принципиально **нет**: `run_command`, `shell`, `exec`, `read_file(path)`,
`write_file(path)`, `list_dir`, `delete_document`, `rename_document`,
`open_url`, `http_request`. Отсутствие инструмента — это и есть запрет, а не
строчка в системном промпте.

Для каждого write-инструмента в анализе должно быть описано:

- область действия (какие документы, какие корни, какие расширения);
- валидация пути (логический ID вместо абсолютного пути, канонизация,
  запрет `..` и symlink-выходов);
- применение в буфер редактора (dirty) и undo; для `propose_create` —
  создание через существующий file-flow (пустой файл + вкладка), содержимое
  в буфере dirty; вариант untitled-вкладки без файла на диске — отдельный
  вопрос анализа;
- проверка устаревшей правки по hash/содержимому;
- политика подтверждения: **всегда diff + «Применить»**; auto-apply вне
  MVP;
- что попадает в audit log.

### 3.3. Интеграция с периметром

- OpenAI-совместимый endpoint: base URL, модель, `/v1/models`, стриминг
  SSE, JSON mode / structured outputs.
- Настройки — `vasyavig.yaml` рядом с `.vasyavig-workspace` (решение
  Q11); секреты — в crypto-формате `crypto__<ENV>__<ciphertext>`, ключ
  Fernet — из env. Plain-ключи не храним. Файл read-only, правки — через
  UI-форму. Образец — `transcript-optimizer` (см. 3.7).
- Несколько моделей в одном конфиге, `default_model` и переключение
  модели во время работы; каждая модель — свой OpenAI-совместимый
  endpoint, параметры и capabilities (streaming/json/tools).
- Другие настройки приложения (`editor`, `assistant`, `files`) — в том же
  файле, с расширяемой схемой; тема и язык остаются глобальными в
  localStorage.
- Ошибки модели: короткий retry, затем ошибка и выбор другой модели;
  автоматического fallback нет.
- Корпоративный TLS: внутренний CA, системный proxy, таймауты, ретраи.
- Ограничения периметра: какие данные можно отправлять, есть ли
  DLP-требования; вариант псевдонимизации — 3.9.
- MVP — несколько моделей в конфиге и ручное переключение; автоматическая
  эскалация и профили «быстрый/сильный» — после MVP; когда и как
  эскалировать, решить отдельно.
- Нужен ли OpenCode server/ACP вообще, если сильная модель доступна по
  тому же OpenAI-совместимому протоколу. Оценить как опцию на будущее, не
  как обязательство MVP.

### 3.4. Безопасность и доверие

- Threat model под новые вводные: модель в периметре, запись разрешена.
- Prompt injection из документа: какие инструменты он может попытаться
  вызвать и почему не сможет выйти за allowlist.
- Защита от галлюцинированной правки: точное `oldText`, уникальность,
  hash, diff, undo; агент не сохраняет на диск, вкладка остаётся dirty.
- Конфиг можно передавать/коммитить: `api_key` (и при необходимости
  `base_url`) — crypto-значения, без env-ключа Fernet файл бесполезен.
  Plain-секретов в файле нет; env-ключ не попадает в репозиторий.
- Аудит (решение 2026-11-02): локально, только метаданные — время,
  модель, тип операции, пути, hash, результат apply. Содержимое документов
  и значения сущностей не пишем; retention настраивается (по умолчанию 50
  запусков).
- Ошибки и отказы: endpoint недоступен, 401/403, таймаут, malformed JSON,
  модель не поддерживает JSON mode.

### 3.8. Предлагаемая структура конфига

Файл `vasyavig.yaml` рядом с `.vasyavig-workspace` (решение 2026-11-02).
Черновик для анализа; не финальная схема. Неизвестные ключи и секции
сохраняются при записи (как `alias` в workspace-файле).

```yaml
version: 1

  editor:
    spellcheck: "ru+en"    # off | ru | en | ru+en
    default_mode: wysiwyg  # wysiwyg | markup | split
    font_size: 14

  models:
    perimeter-fast:
      label: "Быстрая"
      base_url: "https://llm.perimeter.example/v1"

      temperature: 0.2

      context_limit: 32000
      timeout_ms: 60000

        streaming: true
        json_mode: true
        tools: false
      data_scope: perimeter
    perimeter-strong:
      label: "Сильная"
      base_url: "https://llm.perimeter.example/v1"
      model: "qwen2.5-72b-instruct"

      timeout_ms: 120000
      capabilities:
        streaming: true
        json_mode: true
```

Пояснения:

- `llm.models` — карта; ключ — стабильный id модели, `label` — для UI.
- `default_model` — текущая выбранная модель; переключение в UI обновляет
  его (решение 2026-11-02), файл перезаписывается с сохранением
  неизвестных ключей.
- `capabilities` — чтобы рецепт знал, можно ли просить JSON mode и стриминг.
- `data_scope` — для предупреждений; в периметре `perimeter`, локальная
  машина — `local`, публичный интернет — `external`. В MVP все модели
  предполагаются в периметре.
- `app` — `editor`, `files`, `assistant`; тема и язык остаются глобальными
  в localStorage (решение 2026-11-02). Per-workspace переопределения —
  позже.
- `app.assistant.audit` — только метаданные (решение 2026-11-02);
  `retain_runs` ограничивает число запусков.

### 3.9. Псевдонимизация чувствительных сущностей (идея 2026-11-02)

Не «вырезать секреты», а **обратимо заменять** чувствительные сущности
плейсхолдерами: локально найти, замаскировать, отправить в периметр
обезличенный текст, а в ответе модели восстановить исходные значения
(remap). Маппинг живёт только в памяти и никогда не уходит в модель.

Пайплайн:

1. **Detect (локально).** Детерминированные детекторы — API-ключи, токены,
   пароли, e-mail, телефоны, URL с credentials, паттерны `.env`. Плюс NER —
   персоны, организации, локации, при наличии — адреса. NER вероятностный,
   поэтому одних его недостаточно.
2. **Map.** Стабильные плейсхолдеры на запуск/сессию:
   `[[PERSON_1]]`, `[[ORG_2]]`, `[[EMAIL_3]]`, `[[SECRET_4]]`. Одна и та же
   сущность — один и тот же плейсхолдер; проверка на коллизию с текстом
   документа (выбранный разделитель не должен встречаться в документе).
3. **Mask.** Замена только в контекст-паке; в превью отправки — чипы с
   типом и (по клику) исходным значением. Таблица маппинга — только
   память, не в лог и не в audit.
4. **Send.** В промпте — требование сохранять плейсхолдеры дословно, не
   переводить и не перефразировать их.
5. **Validate.** Проверить, что все плейсхолдеры из ответа известны и не
   потеряны. Неизвестный/пропавший плейсхолдер — предупреждение, автоматически
   не применяем.
6. **Unmask.** Восстановить значения в ответе/предложении/diff до показа
   пользователю; проверить, что ни один плейсхолдер не попал в редактор.
7. **Cleanup.** Очистить маппинг после запуска; в audit — только счётчики
   и типы сущностей, без значений.

Ограничения и риски:

- NER пропускает сущности и даёт ложные срабатывания; нужен слой
  детерминированных детекторов и ручное подтверждение.
- Модель может перефразировать, перевести или потерять плейсхолдер —
  полный remap не гарантирован. Для задач, где важны реальные значения
  (письмо с именами, ссылки), псевдонимизацию нужно отключать.
- Локальный NER — это модель и зависимости (ONNX/WASM/сервис), размер и
  качество для ru/en надо оценить отдельно.
- Таблица маппинга — чувствительные данные: только память, без
  persistence и без попадания в логи.
- Плейсхолдеры должны быть устойчивы к регистру/пробелам; для секретов —
  точное совпадение, иначе не восстанавливаем.

Этапность (решение 2026-11-02):

- **A. MVP (выбрано):** детерминированные детекторы + плейсхолдеры +
  ручное подтверждение в превью, без NER. Проверяет сам механизм
  mask/unmask.
- **B. После MVP:** локальный NER как сменный детектор (ONNX/WASM или
  отдельный локальный сервис); типы сущностей настраиваются.
- Режим по умолчанию в MVP — `preview` (показать, подтвердить, отправить);
  `off`/`auto` — позже.
